# Детальное описание 15 этапов UX-процесса

---

## Этап 01 — Вход в задачу

**Цель:** понять проблему, цель, ограничения и источники информации.

**Действия:**
1. Спроси, есть ли документация по задаче (бриф, тикет, переписка, аналитика и т.д.).
2. Если документация есть — прочитай её, зафиксируй выводы и инсайты.
3. Если документации не хватает — собери вопросы и найди дополнительные источники.
4. Запиши пришедшие в процессе идеи и мысли.
5. Выпиши нерешённые вопросы.

**Создаваемые файлы:**
```
01-intake/
  бриф-задачи.md          ← описание задачи своими словами
  доступные-документы.md  ← список найденных источников и материалов
  инсайты.md              ← выводы из изученных материалов
  нерешённые-вопросы.md   ← белые пятна, которые нужно закрыть
  допущения.md            ← что принято за основу без подтверждения
```

**Как понять, что этап завершён:** есть описание задачи, зафиксированы выводы, список открытых вопросов составлен.

---

## Этап 02 — Тип задачи

**Цель:** определить тип задачи и подготовить соответствующий набор файлов.

**Действия:**
1. Определи основной тип задачи из четырёх: улучшение-старого, создание-нового, концепт, исследование.
2. При необходимости укажи дополнительные типы (например, основной — создание-нового, дополнительный — исследование).
3. Зафиксируй тип в `project-state.md`.
4. Подготовь дополнительные файлы, специфичные для типа (см. ниже).

**Создаваемые файлы:**
```
02-types/
  тип-задачи.md   ← основной и дополнительные типы + обоснование выбора
```

**Специфика по типам:**
- **улучшение-старого**: в этапе 07 обязательно создать `как-работает-сейчас.md`.
- **создание-нового**: уделить особое внимание зоне неизвестного-неизвестного.
- **концепт**: ориентироваться на сильное решение без преждевременного урезания до MVP.
- **исследование**: этап 11 становится центральным, а не поддерживающим.

**Как понять, что этап завершён:** тип зафиксирован в `project-state.md`, специфика учтена.

---

## Этап 03 — Основание задачи

**Цель:** зафиксировать, почему вообще решили делать эту задачу.

**Действия:**
1. Спроси: на основании чего решили делать задачу?
2. Зафиксируй основание в свободной форме.
3. Попроси приложить доказательства, если они есть (необязательно).
4. Отдели факты от гипотез.
5. Оцени уровень уверенности (низкая / средняя / высокая).

**Типы оснований с мини-чек-листами:**

| Основание | Ключевые вопросы |
|-----------|-----------------|
| Развитие бизнеса | Как связано с роадмапом? Какое масштабное будущее приближает? |
| Аналитика | Какие данные есть? Какие метрики страдают? Насколько данные надёжны? |
| Технические задачи | В чём техническая причина? Что сломано логически? Legacy или оптимизация? |
| Инициатива команды | Кто инициатор? Почему считает задачу важной? Кого ещё надо опросить? |
| ОС пользователей | Где собрана ОС? Как часто проблема повторяется? Насколько критична? |
| ОС техподдержки | Есть ли аналитика по тикетам? Можно ли подтвердить доп. данными? |
| По фану | Зафиксировать честно: это инициатива без жёсткого обоснования. |

**Создаваемые файлы:**
```
03-основание-задачи/
  основание-задачи.md   ← тип основания, описание, факты vs гипотезы, уверенность, доказательства
```

**Как понять, что этап завершён:** основание зафиксировано, факты отделены от гипотез, уровень уверенности выставлен.

---

## Этап 04 — Инициатор и стейкхолдеры

**Цель:** знать, кого и по каким вопросам нужно спрашивать.

**Действия:**
1. Зафиксируй инициатора задачи.
2. Составь список стейкхолдеров: имя, роль, зона ответственности, какие вопросы к нему.
3. Обновляй список по мере появления новых участников.

**Создаваемые файлы:**
```
04-стейкхолдеры/
  инициатор-и-стейкхолдеры.md   ← список участников, роли, зоны ответственности
```

**Формат файла:**
```markdown
## Инициатор
Имя, роль, контакт

## Стейкхолдеры
| Имя | Роль | Зона ответственности | Вопросы к нему |
|-----|------|---------------------|----------------|
```

**Как понять, что этап завершён:** инициатор зафиксирован, ключевые стейкхолдеры определены.

---

## Этап 05 — Анализ данных и добор ответов

**Цель:** закрыть белые пятна, собрать недостающую информацию.

**Действия:**
1. Проведи анализ имеющихся данных.
2. Зафиксируй выводы и инсайты.
3. Запиши идеи, возникшие в процессе.
4. Выпиши нерешённые вопросы.
5. Попробуй ответить на них через документацию.
6. Если не получилось — найди человека, который поможет (продакт, аналитик, лид-дизайнер).
7. Зафиксируй ответы после созвона или переписки.

**Важно:** не ограничивайся заранее составленным списком вопросов — распрашивай по ходу обсуждения.

**Создаваемые файлы:**
```
05-analysis/
  выводы-и-инсайты.md       ← выводы из анализа, идеи
  нерешённые-вопросы.md     ← открытые вопросы и ответы на них
  ответы-после-встречи.md   ← что удалось выяснить у команды (создаётся при необходимости)
```

**Банк вопросов:** `references/questions-bank.md` → раздел «Общие вопросы» и «Интерфейсные вопросы».

**Как понять, что этап завершён:** основные белые пятна закрыты или зафиксированы как известные неизвестные.

---

## Этап 06 — Референсы

**Цель:** найти похожие решения внутри продукта и при желании снаружи.

**Действия:**
1. Проверь внутренние похожие решения — это обязательный шаг.
2. По желанию собери внешние референсы и конкурентов.
3. Для каждого референса зафиксируй: что это, почему релевантно, что полезно, что нельзя копировать бездумно.

**Создаваемые файлы:**
```
06-references/
  внутренние-референсы.md   ← обязательно
  внешние-референсы.md      ← по желанию
  screenshots/               ← скриншоты референсов
  docs/                      ← документы, PDF, спецификации
```

**Формат записи референса:**
```markdown
## [Название / ссылка]
- Что это: ...
- Почему релевантно: ...
- Что полезно: ...
- Что нельзя копировать бездумно: ...
```

**Как понять, что этап завершён:** внутренние референсы проверены, полезное зафиксировано.

---

## Этап 07 — Текущее состояние

**⚠️ Только для типа «улучшение-старого». Для «создания-нового» этот этап пропустить.**

**Цель:** зафиксировать, как всё работает сейчас.

**Действия:**
1. Опиши текущий user flow (если есть).
2. Зафиксируй edge cases и ошибки.
3. Зафиксируй технические ограничения: что идёт с бэка, что рисуется на фронте.
4. Собери вопросы по сортировке, фильтрации, правам доступа, пустым состояниям.

**Создаваемые файлы:**
```
07-current-state/
  как-работает-сейчас.md      ← текущий flow, скриншоты при необходимости
  ошибки-и-корнер-кейсы.md   ← edge cases, ошибочные сценарии
  технические-ограничения.md  ← что можно и нельзя менять
```

**Как понять, что этап завершён:** текущий flow описан, ограничения и edge cases зафиксированы.

---

## Этап 08 — Цели и критерии успеха

**Цель:** не строить решение в вакууме.

**Действия:**
1. Сформулируй цель задачи.
2. Раздели цели на три слоя: бизнес, пользователь, техника.
3. Зафиксируй метрики успеха, если они есть.
4. Зафиксируй риски и ограничения.

**Создаваемые файлы:**
```
08-goals/
  цель-задачи.md           ← формулировка цели
  критерии-успеха.md       ← как понять, что решение хорошее
  бизнес-цели.md
  пользовательские-цели.md
  технические-цели.md
  риски-и-ограничения.md
```

**Как понять, что этап завершён:** цель сформулирована, критерии успеха определены, риски зафиксированы.

---

## Этап 09 — Гипотезы и варианты решения

**Цель:** сгенерировать несколько вариантов, выбрать направление, не потерять отвергнутые.

**Действия:**
1. Сгенерируй несколько вариантов решения (минимум 2-3).
2. Отметь гипотезы, требующие проверки исследованием или тестом.
3. Зафиксируй выбранный вариант и обоснование выбора.
4. Сохрани отклонённые варианты с причиной отклонения.

**Создаваемые файлы:**
```
09-hypotheses/
  гипотезы.md               ← список гипотез с пометкой "требует проверки"
  варианты-решения.md       ← все сгенерированные варианты
  обоснование-выбора.md     ← почему выбран именно этот вариант
  отклонённые-варианты.md   ← отброшенные варианты + причины
```

**Как понять, что этап завершён:** варианты сгенерированы, один выбран, остальные сохранены с причинами.

---

## Этап 10 — Структура решения

**⚠️ Условный этап. Включать при сложных задачах с множеством экранов и зависимостей.**

**Цель:** собрать архитектуру решения до UI.

**Действия:**
1. Опиши экраны, состояния, действия, переходы — если задача этого требует.
2. Зафиксируй контентные требования при необходимости.
3. Опиши зависимости между экранами и процессами, если они есть.

**Создаваемые файлы:**
```
10-structure/
  структура-решения.md     ← по необходимости
```

**Как понять, что этап нужен:** задача сложная, много экранов, есть ветвления и зависимости.

## Этап 11 — Исследование

**Цель:** проверить гипотезы или закрыть вопросы, которые нельзя решить иначе.

**Действия:**
1. Определи, что именно проверяем (одно исследование может покрывать несколько вопросов).
2. Выбери формат проверки: быстрая валидация, UX-исследование или продуктовый эксперимент.
3. Составь план исследования.
4. Зафиксируй результаты.
5. Сохрани рекомендации по итогам.

**Форматы проверки:**
- **Быстрая проверка** — короткая валидация вопроса или интерфейсного решения.
- **UX-исследование** — осознанный план, сценарий, сбор данных, выводы.
- **Продуктовый эксперимент** — проверка через релиз, метрики, A/B-тест.

**Создаваемые файлы:**
```
11-research/
  план-исследования.md                 ← что проверяем, метод, участники
  результаты-исследования.md           ← что получили
  рекомендации-по-итогам-исследования.md
```

**Как понять, что этап завершён:** гипотезы проверены, результаты зафиксированы, рекомендации сформулированы.

---

## Этап 12 — Артефакты решения

**Цель:** определить, что именно нужно сделать, и вести статус каждого артефакта.

**Действия:**
1. Спроси: что нужно в этой задаче — flow, wireframes, prototype, UI, тест, handoff?
2. Составь список нужных артефактов.
3. Фиксируй статус каждого: не начат / в работе / готов.
4. Не навязывай лишние артефакты, которые не нужны.

**Создаваемые файлы:**
```
12-artifacts/
  список-артефактов.md
```

**Формат файла:**
```markdown
| Артефакт | Нужен | Статус | Ссылка / Путь | Комментарий |
|----------|-------|--------|---------------|-------------|
| User flow | Да | В работе | /figma/link | |
| Wireframes | Да | Не начат | | |
| UI | Нет | — | | Не нужен в этой задаче |
```

**Как понять, что этап завершён:** список артефактов определён, статусы актуальны.

---

## Этап 13 — Тестирование

**⚠️ Только если есть что тестировать.**

**Цель:** проверить решение перед передачей в разработку.

**Действия:**
1. Определи формат тестирования: внутренняя проверка, юзабилити-тест, A/B-тест, постр-релизная проверка.
2. Составь план тестирования.
3. Зафиксируй результаты и список доработок.
4. Прими решение по итогу: оставить / доработать / переделать / отложить.

**Создаваемые файлы:**
```
13-testing/
  план-тестирования.md        ← формат, участники, сценарии
  результаты-тестирования.md  ← что выявили
  доработки.md                ← список изменений, если нужны
  решение-по-итогу.md         ← оставить | доработать | переделать | отложить
```

**Как понять, что этап завершён:** тест проведён, итоговое решение принято и зафиксировано.

---

## Этап 14 — Handoff

**Цель:** передать решение в разработку со всеми необходимыми материалами.

**Действия:**
1. Подготовь файл передачи: что реализуем, ссылки на макеты, спецификации.
2. Если есть открытые технические вопросы — зафикируй отдельно по адресатам (фронт / бэк / QA).
3. Убедись, что у команды есть всё необходимое для реализации.

**Создаваемые файлы:**
```
14-handoff/
  передача-в-разработку.md   ← основной файл с описанием и ссылками
  вопросы-к-фронту.md        ← при необходимости
  вопросы-к-бэку.md          ← при необходимости
  вопросы-к-qa.md            ← при необходимости
```

**Как понять, что этап завершён:** разработчики получили всё необходимое, открытые вопросы зафиксированы.

---

## Этап 15 — Итоги и знания

**⚠️ По необходимости. Особенно полезен для сложных или долгих проектов.**

**Цель:** зафиксировать знания для повторного использования, не потерять опыт.

**Действия:**
1. Создай файл итогов, если задача была значимой.
2. Зафиксируй принятые решения и причины выбора.
3. Обновляй журнал изменений.
4. Перемести устаревшие материалы в архив.

**Создаваемые файлы:**
```
project-management/
  итоги-проекта.md             ← при необходимости
  решения-и-обоснования.md    ← обязательный, ведётся по ходу проекта
  журнал-изменений.md          ← обязательный, ведётся по ходу проекта

15-knowledge/                  ← накопленные знания, паттерны, договорённости
16-archive/                    ← завершённые этапы, устаревшие версии
```

**Как понять, что этап завершён:** знания зафиксированы, архив актуален, проект можно закрыть.
